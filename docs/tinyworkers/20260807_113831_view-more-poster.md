## Goal

### Problem

Rows in the MyTV HTML5 app may end with a “view more” poster whose
`class` contains `.view_more`, whose `item_view_more` attribute is `"1"`, and
whose `content_name` is commonly blank. The current generic `focus_text`
handler searches visible text, so a description that asks for `Xem tất cả`,
`Xem thêm`, or `View more` can focus the wrong text control or fail to find a
target. The current generic `press_ok` also has no destination check for this
poster.

After activation, the poster can open a row-content grid, a service screen, or
show a bottom-right failure tooltip. The runner must distinguish those outcomes
and fail the action when only the tooltip/error state appears.

### Desired outcome

The existing action sequence remains valid:

```json
[
  {"action":"login","username":"<case-username>","password":"<case-password>"},
  {"action":"open_home"},
  {"action":"focus_row","rowName":"Phim mới nhất"},
  {"action":"focus_text","text":"Xem tất cả"},
  {"action":"press_ok"}
]
```

When `focus_text` immediately follows `focus_row` and its text is one of the
three view-more labels, Browser execution focuses the row's trusted
`.view_more[item_view_more="1"]` poster using remote keys. `press_ok` then
requires a non-Home destination with visible content rows, whether the
destination is a row grid or a service screen, and rejects a visible tooltip,
no-data/error popup, or unchanged Home screen. The sample Vietnamese
description compiles to the same five actions.

### Acceptance criteria

- [ ] `focus_text` recognizes `Xem tất cả`, `Xem thêm`, and `View more` as a
      view-more target only when it follows a focused row; it never falls back
      to a same-named menu/control for this target.
- [ ] The helper identifies the focused poster through the fixed trusted DOM
      contract `.view_more[item_view_more="1"]`, tolerates blank
      `content_name`, and reaches a poster outside the initial viewport through
      bounded `ArrowRight` navigation.
- [ ] A row-boundary/no-progress condition fails with the row label and target
      label instead of looping or pressing Enter on another row.
- [ ] After the Enter press, a non-Home grid or service destination with at
      least one visible content row passes; a visible tooltip/toast, recognized
      no-data/error popup, or remaining Home screen fails.
- [ ] `expectedResult: "Vào item \"Xem tất cả\" bình thường"` passes only after
      the view-more destination check and records a view-more result.
- [ ] The sample `qaDescription` including `Di chuyển và focus vào item
      "Xem tất cả"` compiles to login, Home, row focus, text focus, and
      `press_ok` actions without ambiguity.
- [ ] Existing generic `focus_text`, Home `Thể loại` service navigation, direct
      service activation, action validation, and LG/legacy action contracts are
      not regressed.

### Non-goals

## Assumptions, Constraints, and Dependencies

- Assumption: The view-more poster is reachable through the row's normal
  horizontal remote focus order, even when it is initially outside the
  viewport.
- Assumption: A successful row grid or service destination removes visible Home
  row markers and exposes at least one visible content row, matching the
  existing service assertion contract.
- Assumption: The failure tooltip is identifiable through the existing fixed
  `toast|tooltip|notification|snackbar` marker probe or the existing recognized
  failure-popup patterns.
- Constraint: The marker selector and attribute names are trusted code in the
  helper; no selector is read from the case payload.
- Constraint: The shared helper must remain dependency-injectable for pure
  Node unit tests and must use existing `remotePress`/focus observers.
- Dependency: API/server descriptions may arrive with `actions` already
  compiled; the Browser runner must support both explicit actions and the
  deterministic fallback compiler.
- Dependency: The existing `assertServiceOpened()` destination observation
  remains valid for both grid and service view-more destinations.
- Unresolved material questions: None under the Browser-only scope above.

## Risks and Rollback

| Risk | Impact | Mitigation | Rollback or recovery |
| --- | --- | --- | --- |
| The focused class is applied to a child element rather than the poster | The helper could miss a valid view-more poster | Check the focused element and its `.closest('.view_more')` ancestor, require the fixed `item_view_more="1"` marker, and verify row geometry | Revert the content-row/runner changes; existing generic text focus remains unchanged |
| A carousel stops responding or moves focus to another row | The case could loop or activate the wrong poster | Bound attempts, compare focus signatures, require row geometry after each Right, and fail before Enter on no progress | Stop the case and use the attached step diagnostics; no persistent app data is changed by focus-only navigation |
| Grid/service routing differs between staging builds | A valid destination could be misclassified or a failure tooltip could be accepted | Reuse the established non-Home/content-row observer and retain route, rows, popup, and toast details in the failed result | Adjust only the shared destination observer in a follow-up plan; revert the wrapper/runner changes safely |
| The new special case intercepts a legitimate control named “Xem thêm” | Existing generic text flows could change | Activate the special path only after a `focus_row` and only for the exact normalized aliases; otherwise retain `remoteFocusByText` | Remove the alias branch while leaving compiler support for ordinary quoted text |
| Existing uncommitted/generated state is overwritten | Unrelated user changes could be lost | Preserve the clean worktree, use `apply_patch`, review the final diff, and run Graphify only after code changes | Revert only files introduced by this plan; never reset or checkout the worktree |
